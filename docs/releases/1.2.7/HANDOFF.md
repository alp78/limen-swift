## What changed

Android's commit touches 58 files. Each line names the Android file, what it fixed, and where the iPhone carries it.

**Backups and restores** (`Archive.kt`, `ArchiveCrypto.kt`, `Store.kt`, `ArchiveTest.kt`, `StoreTest.kt`, `LegacyCompatTest.kt`; here `ArchiveIO.swift`, `ArchiveCrypto.swift`, `Store.swift`, `ArchiveTests`, `StoreTests`, `LegacyCompatTests`):

- A backup that cannot be made is refused in words. `ArchiveRefused` carries a reason, `unreadableRecord` or `damagedEvidence`, and the record it names; the export applies the test a restore applies (`validEvidence`), so a backup is refused while the original can still be looked at, not found unrestorable on the new phone. `Str.archiveFailure(refused, wholeLibrary)` prints the reason and the remedy for one record or for the whole library; Data, backup and privacy and the record's own backup panel read it. Before, the screen said "backup failed" and a record with a photograph gone from disk went into the archive and was rejected on restore.
- A restore moves its evidence out of the stage instead of copying it (`moveIn` is a rename in the same root). Copying wrote every photograph a second time and ran out of room at an install that the free-space check never covered, which counted valid records as rejected. Records the stage holds with no record file, what a restore killed during its install leaves since the JSON is written last, go into `recovery/<id>/archive-<uuid>` with the rest, never deleted.
- A wrong password is refused after the first decrypted chunk. Every archive the reader accepts opens with a ZIP local header (`50 4B 03 04`) because the manifest is an entry, so noise there throws `ArchiveError.wrongPassword` at once instead of after the whole backup has been decrypted to disk; the tag is still checked at the end for a right password.
- What a killed restore or amendment leaves behind is swept once per process at start: `Store.sweepStale()` removes the decrypted copy (`archive-decrypt-`), the unpacked stage (`.archive-import-`) and a half-copied amendment folder (`photos/.amend-`) whatever their age, off the main thread because after a killed restore it unlinks gigabytes, and the model holds `archiveBusy` until it returns so a restore tapped meanwhile cannot start a stage the sweep then deletes. The stage of 1.2.5 was removed only by the next restore.
- An amendment's evidence is copied through `Store.saveAmendment(parent:draft:)`: the photographs and documents the draft refers to are copied under `.amend-<id>`, then renamed into place, and the JSON is written last, so a failure leaves nothing a list would show and nothing `delete` would ever be asked for. Android's `Store.kt` does the same; the old port copied in the model with the folder visible from the first file.
- A recovery that fails says so: `recoverFailedId` and `Str.recoverFailed` under the unreadable entry, instead of a key that did nothing.

**The gate, the ticks and the messages** (`CompletionRules.kt`, `CompletionActions.kt`, `CompletionRulesTest.kt`, `InputValidationTest.kt`; here `CompletionRules.swift`, `RecordPanels.swift`, `DossierStep.swift`, `RulesTests`, `ParityRulesTests`):

- One definition per rejected value. The gate, the dossier's section ticks and the messages that name the cause ask the same predicates (`readingFaulty`, `attachmentFaulty`, `followUpFaulty`, `estimateFaulty`, `contractValid`, `transferValid`, `invalidAmount`), so a ticked chip cannot sit beside a blocked FINALIZE with nothing on screen naming what is missing. A section ticks only when it holds something and the gate has nothing to say about it.
- The messages name what they reject. `dossierCauses` lists each value the dossier check refused by the name it carries on screen, where the old message sent a person to Deposit, Meters and Attachments whenever they existed while the cause sat in a rent, a wear estimate or a follow-up; `timeCauses` names the actual transfer and each reading whose time is not one, since the time issue's own wording names the handover time alone. The hub's object warning no longer shows for a reading's time: only the handover time itself belongs to the object.
- The deposit amount is read as the Deposit card shows it (`depositAmountShown`): only the two kinds that print an amount have a field, and the pill left the typed text behind when it moved to None or Unknown, so the gate blocked finalization over a value nobody could reach. The deposit target is gated on the card, as the gate asks it.
- The Keys answer is gated on the Keys card like every other component: removing the card takes the answer with it and the reason for the removal stands in for the outcome.
- The estimate's date is gated here as well, which Android does not do: the field keeps a half-typed date verbatim and the paper prints it as typed. Recorded as an iOS extra.

**The paginator and the sheet** (`pdf/Paginator.kt`, `pdf/Sheet.kt`, `pdf/Annex.kt`, `PaginatorTest.kt`, `PdfPlatesTest.kt`; here `PdfPaginator.swift`, `PdfSheet.swift`, `PdfAnnex.swift`, `PaginatorTests`):
