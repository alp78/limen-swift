# Limen, the iOS port

Native Swift/SwiftUI port of the Android original at `/Users/aperi/DEV/ANDROID/limen` (from this repo: `../../ANDROID/limen`). The Android source is the specification: its product decisions are deliberate, its comments carry the reasons, and those reasons apply here unless iOS genuinely cannot honor them. The authorised October 2026 audit adds Android 1.2 parity and justified iOS usability repairs while preserving the product identity. Do not drop behaviour for being awkward.

## The record in the app's own style, 21 October 2026

Android 1.2.6 (versionCode 11, `origin/main` at `8254bdc`) redrew the exported record in the app's own style on the owner's request of the day, and this port followed the same evening, recorded in [the 1.2.6 handoff](docs/releases/1.2.6/HANDOFF.md). Page 1 is a cover: the landing's navy banner with the seal, the protocol kind and the handover kind as a pill, then the rental object, the parties, the record's status with its reference and fingerprint, and the contents with each section's page. The counting pass learns those pages and the page each annex section opens on; the export checks that the sections drawn are the sections planned after each pass and that the second pass broke its pages where the first did, and refuses the document otherwise, because a contents that lies under a signed record is worse than no export. Each room is one panel, amber when it holds findings, its status as a pill, the findings inside with the number in a navy badge, the landlord's claim as an active chip, and chips for the photograph count and the annex page. Independent facts never share a line joined with a middle dot: `RecordContent` prints them one per line, with a colon for a label and parentheses for a role. The annex keeps the 1.2.5 composition and takes the panel look, each plate clipped to the thumbnail corners under a navy border; the clip is a path in the content stream and the plate stays one DCT image with no soft mask. The HTML copy carries the same panels, pills, chips, findings and contents list in Android's stylesheet, with the iPhone's face first and without the measure cap on `main`. `LimenPalette` in LimenKit is the one source of the Day colours for the SwiftUI theme and the paper; two of its values differed from Android's since the audit (`warningOutline` `#835000`, `disabledInk` `#A7ADB8`) and now follow it. Version is 1.2.6 build 8, built in Release on the iPhone, committed as `d112d8f` and uploaded from that commit the same evening (delivery `9fa56942-a00b-411d-a728-e8d4531a4915`): in the Owner and Agencies TestFlight groups with its four "What to Test" notes, submitted for Beta App Review, and attached to the store version, renamed from 1.1.2 to 1.2.6 and not submitted for sale; the five-language notes and the TestFlight note are in [docs/releases/1.2.6/RELEASE-NOTES.md](docs/releases/1.2.6/RELEASE-NOTES.md). ## Annex by room, unbounded backups and JPEG XL, 21 October 2026

Android 1.2.3, 1.2.4 and 1.2.5 (versionCodes 8 to 10) were ported in one pass recorded in [the 1.2.5 handoff](docs/releases/1.2.5/HANDOFF.md); the Android reference is `origin/main` at `94c7cf7` (1.2.5, versionCode 10). The photo annex is a photographic report: a contents page with page numbers, one section per room opening on its own page, each photograph framed and large with its legend beside a tall one and under a wide one, the legend repeating the room, the finding's number and words, the surface, who is held to it and when it was taken, and no hash. Each plate is one JPEG at libjpeg's quality 85 (ImageIO's 0.60, calibrated to it) fitted to 1020 by 1100 sheet units at 4/3 pixels per unit (200 dpi), written once into a spool, carried by the PDF as that very DCT stream and embedded by the HTML copy as the same bytes; the export writes files, never a Data of the whole document. Every size limit went: the archive, its entries, the record JSON, the photo and document intake; the ZIP writer and reader stream, write and read ZIP64, and the restore and the decrypt staging check the volume's free space once per megabyte. A backup repacks its JPEG photographs losslessly as JPEG XL through libjxl 0.12.0 built from pinned sources, says `version=2` in its manifest when any photograph was repacked, and rebuilds every one byte for byte on restore; a backup without a repacked photograph stays version 1. Version was 1.2.5 build 7, built in Release and never uploaded, superseded the same day by 1.2.6 build 8; the five-language release notes written for build 7 are in [docs/releases/1.2.5/RELEASE-NOTES.md](docs/releases/1.2.5/RELEASE-NOTES.md) and folded into build 8's. `ThirdParty/` is gitignored: `make deps` and `make jxl` rebuild it, and `make gen` stops when it is missing.

New participants use stable IDs; historical records are read without inserting IDs or changing signed canonical bytes. Every tenant keeps an independent position and reservation. New room/meter photographs, supporting documents, access devices, later findings and residual-value inputs use the Android 1.2 schema. An amendment owns copied evidence and leaves its parent untouched.

The Apple graphics PDF remains untagged. Use the semantic HTML companion for structured access; automated accessibility audits and screenshots are evidence, not a substitute for a human VoiceOver or native-language review. Permission-purpose strings are localized in the built app; iOS chooses their language separately from the in-app document language.

## Decisions, settled 2026-09-04

| Decision | Choice | Reason in one line |
|---|---|---|
| Deployment target | iOS 17.0, current SDK | Android minSdk 29 keeps 2019 handsets; 17 reaches 2018 iPhones and keeps Observation, which the model is built on |
| UI framework | SwiftUI, every screen; rotates | The original is custom Compose over one embossed key kit; nothing uses platform chrome UIKit would do better |
| The record | One value type per Kotlin data class, enum raw values are the Kotlin names, field order is the Kotlin declaration order | The JSON on disk and in the archive is the Android file byte for byte, so a backup restores across phones |
| JSON | An ordered `JSON` tree and one writer per type with the Android `@EncodeDefault(NEVER)` marks; kotlinx's compact form and escape table; reading through a bounded ordered parser with strict nonnullable types and nested-map order preserved | Foundation's encoders order keys by hash or alphabetically; the fingerprint hashes the text, so the order is part of the contract |
| Fingerprint | SHA-256 over the canonical text plus every photo and ink hash, labels sorted by UTF-16 units | `LegacyCompatTests` pins the Android suite's own golden hex: a record signed on either phone verifies on the other |
| Store | JSON files under Application Support, photos and ink beside them, excluded from backup, written through a scratch file and a POSIX rename, with monotonic sequence checks, frozen-content protection, a visible unreadable catalogue and last-good recovery | filesDir's iOS shape, and the manifest's allowBackup=false |
| Archive | Own streaming ZIP writer and reader (raw DEFLATE through Compression's stream API, CRC-32 table, ZIP64 records wherever a size, an offset or a count needs them, both directions checked against Python's zipfile), the manifest written last and the name rules as on Android; no limit on the archive, an entry or the record JSON since 1.2.5; since 1.2.7 an export is refused in words when a record cannot be read or its evidence would fail the restore's own check, a restore renames its evidence out of the stage and quarantines orphaned folders under `recovery/`, a wrong password is refused after the first decrypted chunk, and the store sweeps a killed restore's or amendment's stage once at start | iOS has no public ZIP API and the archive has to be read by java.util.zip and read from it; the reader trusts the central directory because Java writes data descriptors, and the writer patches its local headers in place instead of writing descriptors because Java's ZipInputStream refuses a stored entry that carries one. Thirty camera originals weigh 69 MB, so the 64 MiB cap meant a real record could not be backed up; the intake, the decode and the restore stream, and the restore and the decrypt staging check the volume's free space once per megabyte, two megabytes ahead, so a backup larger than memory saves and restores and a full phone fails with its reason instead of a half-written store |

An unprotected archive needs no new reader and no new version, and the screen says in the warning colour which the person chose. The limits of 1.2.0 to 1.2.2 (8 MiB JSON, 64 MiB entries, 256 MiB expansion, 20,000 entries) went with Android 1.2.3: an entry is inflated in pieces straight to its file and never held whole, so a declared size claims nothing at once, and a size that lies is refused when the inflated bytes pass it. ## House rules

- SF Symbols only for control glyphs. The seal is the app's own artwork and exempt; the 26 canton flags are the public-domain data assets the Android app ships and identify a canton beside its name. No found, stock, or AI-generated images.
- Never a control that implies a capability the app lacks: the camera key says so when there is no camera, the export key is disabled on a draft, the exit key on an entry card says to finalize first.
- No em-dashes, no period ending a title or heading, never "land" as a verb for data or files. In comments and UI strings alike.
- Comments explain why: the constraint or the bug that forced the shape. Port the Android comments' reasons with the code they explain.
- Signed only as the owner's own account (aperinger@proton.me, team KDSZB7N44K), which is the one that will hold the paid membership. Never build for the device before the pin exists: an identifier registered once by a team is closed to every other, which is why the previous namespace had to be abandoned.
- One network call, the swisstopo address suggestion, and only while the person asks. Camera permission and optional Face ID purpose for the library/settings gate. Records leave as PDF, HTML or an explicitly chosen protected/plain archive.

## Platform differences accepted

- The camera asks for its permission once. Android took photographs through the system camera app with no permission of its own; iOS has no such route.
- There is no system back gesture and no predictive back animation. The back key on every screen carries the way out, as it did on Android beside the gesture.
- The Android page is 1240 by 1754 points; here it is A4 with the same drawing scaled onto it, so a print at 100 percent is the size the form was meant to be.
- The backup password dialog is a system alert with two secure fields, and the confirmations are system alerts.
- The exported files are in Documents/Limen (Files: On My iPhone / Limen), not a Downloads collection, and are named `<address>-<handover day>.pdf` where Android's name carries the kind, the language, the fingerprint and the export time as well.
- The photo library can hand over a HEIC original, which the camera on Android never produces; it is not a JPEG, so it is neither repacked in a backup nor touched, and travels as it is.
- The document's face is San Francisco where the Pixel's is Roboto, at the same sizes, weights and line heights; a line that wraps differently can move a page break, so the page count of the same record may differ by a page between the phones. The draft preview also names each participant whose outcome is still missing inside the signature panel, which Android's preview does not; a finalized record prints the same as Android's.

## The loop

```bash
make deps     # fetch libjxl, Brotli, Highway and skcms at their pinned hashes into ThirdParty/libjxl
make jxl      # build ThirdParty/LimenJxl.xcframework for the iPhone and the simulator
make strings  # regenerate Str.swift from the verified Android source and iOS overrides
make schema   # regenerate ordered model/codec definitions
make check-generated # check deterministic generators against LIMEN_ANDROID
make phones   # regenerate PhoneMetadata.json from the pinned libphonenumber XML
make marks    # copy the seal, the flags and the mark from the Android repository
make gen      # tuist generate, no open
make build    # simulator build
make test     # AllTests scheme
make lint     # swiftlint
make run      # build + install + launch on the simulator
make icon     # write the app icon from the seal
make shots    # pull the UI test screenshots out of the newest result bundle
make device   # build Release + install + launch on the connected iPhone
```

Debug builds accept the launch arguments `LIMEN_RESET` (clears the store and the preferences) and `LIMEN_DEMO` (seeds the Android instrumentation's draft and opens it), and the environment variable `LIMEN_LANG` (`En`, `Fr`, `De`, `It`, `Rm`). The UI smokes attach a screenshot to every step, and `make shots` exports them from the newest result bundle into `DD/shots` under the names the tests gave them; nothing in the scheme sets `LIMEN_SHOTS`, so the result bundle is where they actually are.

Tuist resolves source and resource globs at `make gen`: a new file compiles only after regenerating. Synthesized asset accessors are off, because they would generate a `LimenColors` type over the palette.

Release acceptance requires a Release build and launch on the owner's physical iPhone, with screenshots for visual work. Record unexecuted gates honestly; a successful simulator build is not physical verification. Git belongs to the owner: never commit or push; end each piece of work with paste-ready `cd`, `git add`, `git commit -m` and `git push` commands as one line, one-line message, no trailing period, no attribution.
